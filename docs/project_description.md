# Платформа помощи гражданам — описание проекта

## 1. Описание проекта

**Цель:** сервис для приёма и обработки обращений граждан по городским проблемам (ямы на дорогах, освещение, ЖКХ и т.п.). Гражданин создаёт заявку через Telegram-бота; оператор назначает тип и исполнителя, проверяет доказательства выполнения (пруфы); исполнитель отчитывается о работе. После подтверждения пруфа гражданин может поставить оценку (1–5) и оставить текстовый отзыв.

**Пользователи системы:**

| Роль | Интерфейс | Основные действия |
|------|-----------|-------------------|
| **Гражданин** | Telegram-бот | Создание заявок, просмотр статусов, уведомления, оценка и отзыв |
| **Оператор** | Telegram-бот | Заявки, назначение типа и исполнителя, проверка пруфов |
| **Исполнитель** | Telegram-бот | Назначенные заявки, смена статуса «В работу», загрузка пруфов |
| **Суперпользователь** | `/admin` (веб) + бот | CRUD по всем сущностям; в боте видит все заявки, как оператор |

**Польза:** единый канал подачи обращений, прозрачные статусы, проверка пруфов оператором, обратная связь от гражданина.

### Архитектура (как в коде)

- **Бэкенд:** FastAPI, SQLAlchemy (async), PostgreSQL, миграции Alembic.
- **Фронт для пользователей:** Telegram-бот (`python-telegram-bot`, режим polling).
- **Связка:** бот и API работают в **одном процессе** — бот стартует в `lifespan` FastAPI (`app/main.py` → `app/bot/app_factory.py`). Бот обращается к REST API по HTTP (`app/bot/api_client.py`).
- **Админка:** SQLAdmin на `/admin`, вход по логину и паролю суперпользователя (bcrypt, сессия).
- **Развёртывание:** Docker Compose — сервисы `app` (API + бот) и `db` (PostgreSQL 16).

**Ограничения MVP (важно для понимания):**

- Маршруты `/api/*` **не защищены JWT** — разграничение ролей выполняется в боте по `telegram_id`.
- При создании заявки оператор назначается **автоматически только если в системе ровно один** пользователь с ролью `operator`.
- Типы заявок — справочник; оператор назначает тип вручную. Автомаршрутизация по категориям/районам не реализована.
- Правки в админ-панели идут **напрямую в БД** и **не вызывают** уведомления в Telegram и смену статусов (эта логика — только через бота и API).

## 2. Пользовательские сценарии

### Команды бота (общие)

| Команда | Назначение |
|---------|------------|
| `/start` | Регистрация или приветствие по роли |
| `/new` | Создать заявку (только гражданин) |
| `/list` | Список заявок (фильтр по роли) |
| `/help` | Справка по роли |
| `/skip` | Пропустить фото заявки, фото пруфа или текстовый отзыв |

Навигация по заявкам — **inline-кнопки** под сообщениями (без постоянного нижнего меню).

### Гражданин

1. **Регистрация** — `/start`: если пользователя с таким `telegram_id` нет, создаётся учётная запись с ролью `citizen` (без пароля).
2. **Создание заявки** — `/new`, четыре шага: **название → адрес → описание → фото** (фото можно пропустить через `/skip`). Заявка получает статус «Создана»; при единственном операторе в системе — автозакрепление за ним и уведомление оператору.
3. **Просмотр** — `/list` → выбор заявки. В карточке гражданину **не показываются** ФИО оператора и исполнителя.
4. **Уведомления** — при смене статуса, назначении типа, решении по пруфу (с текстом и фото пруфа при наличии), кнопка «Открыть заявку».
5. **Оценка и отзыв** — для заявки в статусе «Выполнена» в карточке кнопки 1–5; затем текстовый отзыв или `/skip`. Данные сохраняются в полях заявки `rating`, `citizen_review`, `citizen_confirmed`.

### Оператор

1. **Вход** — учётная запись с ролью `operator`, `telegram_id` и паролем создаётся **суперпользователем** в `/admin`. При `/start` бот находит пользователя по Telegram ID.
2. **Список заявок** — `/list`: заявки, назначенные оператору, и новые без оператора (статус «Создана»).
3. **Карточка заявки** — полные данные: гражданин, оператор, исполнитель, тип, фото проблемы.
4. **Назначение типа** — кнопка «Назначить тип» / «Изменить тип»; выбор из справочника (`request_types`, сид: `python -m scripts.seed_request_types`).
5. **Назначение исполнителя** — кнопка «Назначить исполнителя»; после выбора API переводит заявку в «В работе», уведомления исполнителю и гражданину.
6. **Пруфы** — кнопка «Пруф» / «Пруфы (N)»: просмотр текста и фото, «Подтвердить» / «Отклонить». Подтверждение → «Выполнена», отклонение → «В работе»; уведомления гражданину и исполнителю.

### Исполнитель

1. **Вход** — как у оператора: запись создаёт суперпользователь в `/admin` с `telegram_id`.
2. **Список** — `/list`: только заявки с `assigned_executor_id`, равным текущему пользователю.
3. **«В работу»** — кнопка в карточке, если заявка в статусе «Создана» и уже назначена этому исполнителю.
4. **Пруф** — «Прикрепить пруф»: **обязательный текст** описания работы (с предупреждением, что пруф видят оператор и гражданин), затем **фото** или `/skip`. Заявка переходит в «На проверке пруфов»; оператор получает уведомление.

Исполнитель **не** переводит заявку в «Выполнена» сам — только через проверку пруфа оператором.

### Суперпользователь

1. **Создание учёток** — в `/admin` (CRUD пользователей): роли `operator`, `executor`, `superuser`; для сотрудников указываются `username`, `password_hash` (пароль в форме), `telegram_id`.
2. **Первый суперпользователь** — скрипт:
   ```bash
   python -m scripts.create_superuser --username admin --password secret --telegram-id 123456789
   ```
   `telegram_id` опционален, но нужен для работы в боте.
3. **Управление данными** — CRUD: пользователи, заявки, типы заявок, пруфы.
4. **В боте** — `/list` показывает **все** заявки; действия как у оператора (тип, исполнитель, пруфы).

### Жизненный цикл заявки (статусы)

```
Создана → В работе → На проверке пруфов → Выполнена
                ↑__________________________|  (пруф отклонён)
```

Дополнительно в модели есть статус `rejected`; в типовом сценарии бота основной путь — через пруфы.

### REST API (кратко)

Префиксы: `/api/users`, `/api/requests`, `/api/proofs`, `/api/request-types`. Документация: `/docs`, `/redoc`.

Примеры: `GET /api/users/by-telegram/{id}`, `POST /api/requests/`, `PATCH /api/requests/{id}`, `POST /api/proofs/`, `PATCH /api/proofs/{id}/decide`.

## 3. Глоссарий

- **API** — REST-интерфейс FastAPI; бот и (в перспективе) веб-клиент обращаются к нему по HTTP.

- **Бэкенд** — FastAPI-приложение + PostgreSQL: хранение данных, бизнес-правила (статусы, пруфы, автоназначение оператора).

- **Фронт** — Telegram-бот; единственный пользовательский интерфейс в MVP. В перспективе — веб для операторов с JWT к тому же API.

- **Telegram-бот** — `python-telegram-bot`, polling; команды и inline-кнопки; уведомления через `notify_user_id` (Bot API).

- **Заявка** (`CitizenRequest`, таблица `requests`) — обращение: название, описание, адрес, `photo_file_id`, статус, назначенные оператор/исполнитель, тип, оценка и отзыв гражданина.

- **Статус заявки** — `created`, `in_progress`, `proof_under_review`, `completed`, `rejected` (в боте отображаются по-русски через `app/labels.py`).

- **Пруф** (`Proof`, таблица `proofs`) — отчёт исполнителя: обязательный `comment`, опциональное фото (`file_ref` — чаще `file_id` из Telegram). Статусы пруфа: `pending`, `approved`, `rejected`.

- **Тип заявки** (`RequestType`) — справочник категорий (например, «Дороги», «ЖКХ»). Оператор назначает вручную; автоматического распределения по типу нет.

- **Оператор** — принимает поток заявок, назначает тип и исполнителя, решает по пруфам.

- **Исполнитель** — выполняет работу, загружает пруф; создаётся суперпользователем.

- **Суперпользователь** — полный доступ к `/admin` и расширенный обзор в боте. Вход в админку: `username` + пароль (роль `superuser`).

- **Роль** — `citizen`, `operator`, `executor`, `superuser`; определяет доступные кнопки в боте (`app/bot/keyboards.py`).

- **База данных** — PostgreSQL 16; ORM SQLAlchemy async; миграции Alembic (`alembic upgrade head`).

- **Docker / Docker Compose** — контейнеры `app` и `db`; запуск: `docker compose up --build`.

- **SQLAdmin** — веб-админка на `/admin` для суперпользователя.

- **Swagger** — интерактивная документация API на `/docs`.

- **Alembic** — версионирование схемы БД.

- **MVP** — рабочий прототип без JWT на API, без веб-фронта для граждан, без автомаршрутизации по типам заявок; достаточен для демонстрации и курсовой работы.
